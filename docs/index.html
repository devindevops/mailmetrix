Take control of your diagnostic environment.

Email troubleshooting can involve SMTP credentials, DNS configuration, and sensitive message headers. MailMetrix provides a self-hosted deployment option so you can run diagnostics in infrastructure you control.

🏠

Self-hosted by design

Build and run the application in your own environment using Docker Compose.

🎯

Focused email diagnostics

Access common SMTP, DNS, header-analysis, and authentication-generation tools in one interface.

Self-hosting can reduce dependence on third-party diagnostic services, but it does not automatically guarantee security. MailMetrix includes built-in safeguards, but it has no built-in login, so protect access to your deployment. See the Security section.

Four tools. One self-hosted workspace.

Explore the tools available in MailMetrix.

01. SMTP Tester

Troubleshoot SMTP connectivity and authentication against a specified mail server. Private and internal addresses are blocked by default, and only standard mail ports are allowed.

02. DNS Email Checker

Inspect MX, SPF, DMARC, and DKIM records associated with your domain.

03. Email Header Analyzer

Examine email headers to investigate message routing and authentication information.

04. DKIM & DMARC Generator

Generate email authentication configuration material for review and deployment. Key generation runs off the main thread with a concurrency limit.

Simple, containerized architecture.

MailMetrix separates the frontend interface from the backend API and builds the application from source.

🌐

Frontend

Unprivileged Nginx · Web interface · API proxy

⚙️

Backend

Node.js · Diagnostic API · Not published to the host

Only the Nginx container is published (host port 50000); the backend is reachable only through the proxy or from the Compose network. SMTP and DNS operations may communicate with external servers or resolvers. Review the source code to understand the connections made by each feature.

Run MailMetrix yourself.

Start with the public source repository and build the application on your own machine.

git clone https://github.com/devindevops/mailmetrix.git cd mailmetrix docker compose build docker compose up -d

Open http://localhost:50000 after the containers start. Review the README and its Configuration section before deployment, especially before exposing the instance to any network beyond your own machine.

Safeguards built in. Responsible hosting required.

MailMetrix includes protections against common abuse of a diagnostic tool, but self-hosting still requires you to protect credentials, limit access, and understand how requests are processed.

Built-in safeguards

🛡️

Outbound connection guardrails

The SMTP tester validates its destination before connecting. Loopback, private, link-local, and cloud-metadata addresses are blocked, the validated address is the one connected to, and ports are limited to 25, 465, 587, and 2525 by default.

✉️

Email abuse limits

Sender and recipient must each be a single valid address, and subject and message length are capped. Operators can restrict recipients with ALLOWED_RECIPIENT_DOMAINS or ENFORCE_TEST_RECIPIENT.

⏱️

Rate limiting

Every API route is limited per client IP, with stricter limits for SMTP tests, record generation, and DNS checks. Limits are configurable through environment variables.

🧮

Bounded resource use

DKIM key generation runs off the main thread with a concurrency cap and bounded queue. When the server is busy it answers 503 instead of stalling.

🧱

Hardened web layer

Nginx sends Content Security Policy and other security headers, hides its version, and strips backend framework headers. The public health probe reveals no process internals.

📦

Least-privilege containers

Both containers run as non-root users with all Linux capabilities dropped and privilege escalation disabled. Base images are pinned to supported versions.

Your responsibilities

🔐

Add authentication

MailMetrix has no built-in login. Do not expose it to untrusted networks without reverse-proxy authentication, an identity-aware gateway, or a private network such as Tailscale or WireGuard.

🔑

Protect credentials

Never commit secrets. Avoid production credentials during testing, and review application logging.

🔀

Configure the proxy chain

Set TRUST_PROXY to the number of proxies in front of the backend so rate limiting sees real client addresses, and use HTTPS for remote access.

🔄

Keep everything updated

Pinned images and dependencies do not update themselves. Rebuild regularly, and consider automated update tooling.

These safeguards reduce risk but do not replace authentication or network controls. Rate limits are in-memory and per process, and recipient restrictions based on user-supplied fields limit blast radius rather than prevent abuse. Read the full details in the README security section.
